# Instructions for working in this repo

## Never use em dashes ("—")

Do not use the em dash character (—) anywhere in this repo: page copy,
JSON-LD/structured data, code comments, commit messages, or
documentation. This applies to every file, not just rendered HTML.

Write the sentence a different way instead:
- Two related clauses: use a comma, semicolon, or colon depending on how
  they relate (`", "`, `"; "`, `": "`).
- A short interrupting aside: use parentheses, e.g. `"the tools you
  already use (CRMs, email platforms, and more)"`.
- Two independent sentences: just end the first one with a period and
  start a new sentence.

This rule was added after a sitewide sweep to remove every existing em
dash from the site's HTML, JSON-LD schema, CSS comments, and
documentation, so the codebase is currently clean. Keep it that way.

## How the site is built

Every page is generated by `npm run build` (Node 18+, no dependencies) and
the output is committed. The deploy workflow only syncs files to S3, so
always run the build and commit the result after changing a source file.
Never hand-edit generated HTML; it is overwritten on the next build.

Sources:
- `content/automations.json`: every automation (industry, business function,
  role, step-by-step copy, manual process, tools). Each one gets its own page
  at `/automations/<industry>/<slug>/`.
- `content/taxonomy.js`: the 11 business-function categories, the tool pages,
  and the per-industry intro copy.
- `content/solutions/<category>.json`: platform solutions, one file per
  category. Each category gets a page at `/solutions/<category>/` and each
  solution a page at `/solutions/<category>/<id>/`. The Solutions menu in
  `build/lib/chrome.js` (`NAV_SOLUTIONS`) must list the same categories; the
  build fails if they drift.
- `content/guides/*.html`: long-form guides. Metadata lives in a JSON comment
  at the top of each file; `<h2>` headings feed the table of contents.
- `content/pages/`, `content/faq.json`: static page copy (legal text, FAQ,
  quiz script).
- `build/`: the generator. `build/pages/*.js` render each page type.
- `assets/css/site.css` and `assets/js/site.js`: the design system and site
  script.

## Shared with the blog repo

`blog.ljwebmanagement.com` uses the same header, footer, design system and
site script so the two sites feel like one. These files must stay identical
in both repos:

| This repo | Blog repo |
| --- | --- |
| `build/lib/chrome.js` | `scripts/chrome.js` |
| `assets/css/site.css` | `assets/css/site.css` |
| `assets/js/site.js` | `assets/js/site.js` |

When you change one, copy it to the other repo and rebuild both
(`npm run build` here, `npm run rebuild` in the blog). The blog loads this
site's search index from `/assets/data/search-index.js`, and this site loads
the blog's latest posts from `https://blog.ljwebmanagement.com/assets/js/latest-posts.js`.

## Privacy and accessibility rules

- Third-party scripts that track or record visitors (analytics, session
  recording, ad pixels) must only load through `analytics()` in
  `build/lib/chrome.js`, never directly on a page. Analytics run by default
  and stop when a visitor opts out from the cookie banner or Your Privacy
  Choices. Live chat is the standard Tawk.to widget from `chatWidget()`.
- The choice is the `lj_consent` cookie on `.ljwebmanagement.com`, shared by
  www and the blog. Bump `CONSENT_VERSION` in `chrome.js` to show the banner
  to everyone again after adding a new kind of tracking, and update the
  Privacy Policy (`content/pages/privacy-policy.html`) in the same change.
- Global Privacy Control and Do Not Track signals count as an opt-out.
- New pages must pass an axe-core WCAG 2.1 AA check, work by keyboard, and
  keep visible focus. Videos need captions (see `assets/homepage-video.vtt`).
